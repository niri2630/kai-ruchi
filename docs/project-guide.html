01

What you have actually built

Kai Ruchi is a working online shop. Not a design, not a mock-up — a real one. You can browse products, search them, put them in a basket, make an account, pay, and then watch your order move from "placed" to "delivered".

It sells the food a single home kitchen in Udupi makes: masalas, pickles, fresh batters, fried snacks and sweets. Fourteen products across five categories.

What a visitor can do

  • Browse — a home page, five category pages, and a page for every product.
  • Search — type a word and matching products appear instantly as you type.
  • Filter and sort — by category, by how spicy it is, vegetarian or not, in stock or not, and by price or rating.
  • Add to a cart — which works even before you log in, and follows you into your account when you do log in.
  • Make an account — sign up, sign in, edit your details, save delivery addresses.
  • Check out and pay — enter a delivery address and pay (on a simulated payment screen — see section 8).
  • Track the order — a six-step timeline showing exactly where the parcel is.
  • Write reviews — and reviews are marked "verified" automatically if that account really bought the product.
  • Contact the shop — a contact form that saves the message into the database.
Say this out loud

The one-sentence description

"It is a full-stack e-commerce web application. The frontend is built with Next.js and React, the backend is a REST API built with FastAPI in Python, and the data is stored in a PostgreSQL database with Alembic managing the schema changes."

What it deliberately does not have

There is no admin dashboard. That was a scope decision — it is a mini project, not a business. Two consequences follow, and it is worth knowing them because a teacher may well ask:

  • Orders move on a timer. A real shop has staff clicking "packed" and "shipped". Here, once an order is paid, it walks itself along the tracking timeline over about 35 minutes so it can be demonstrated live.
  • Products are added by editing a seed file (backend/app/seed.py) and re-running it, rather than through an admin screen.

The words you need to know

Learn these ten and you can hold any conversation about this project. Everything else is detail.

WordWhat it actually means
FrontendEverything the user sees and clicks — the pages, buttons, images, animations. It runs inside the visitor's browser.
BackendThe program running on a server that the frontend talks to. It does the thinking: checking passwords, calculating totals, saving orders. Nobody sees it.
DatabaseWhere information is permanently stored — users, products, orders. If the server restarts, the database still remembers everything.
APIThe list of things the frontend is allowed to ask the backend for. Like a restaurant menu: "give me all products", "add this to my cart".
EndpointOne single item on that menu. For example GET /api/products means "give me the products".
RESTThe common convention for designing those menus, using web addresses plus verbs — GET (fetch), POST (create), PATCH (change), DELETE (remove).
JSONThe text format the frontend and backend use to send information to each other. Looks like {"name": "Mango Pickle", "price": 279}.
SchemaThe shape of the database — which tables exist and what columns they have.
MigrationA recorded change to that shape. Instead of editing the database by hand, you write a migration, so the change can be repeated on any computer.
DeployPutting the project on the internet so anyone can visit it, instead of only on your own laptop.

Two more that sound scary

JWT (JSON Web Token) When you log in, the backend gives your browser a long signed string. Your browser sends it with every later request, which is how the server knows it is still you without asking for your password again.
ORM (Object-Relational Mapper) A translator between Python code and database tables. Instead of writing SQL by hand, you write db.query(Product) and the ORM — here, SQLAlchemy — writes the SQL for you.
03

The three pieces, and how they talk

Every full-stack project is the same three boxes. Once you can draw this on a whiteboard, you understand the architecture.

BROWSER  (the visitor's phone or laptop)
│
Next.js frontend — pages, buttons, animations
│
▼   asks for data over HTTPS, in JSON
│
FASTAPI BACKEND  (a Python program on a server)
checks passwords · calculates totals · applies the rules
│
▼   reads and writes rows via SQLAlchemy
│
POSTGRESQL DATABASE
users · products · carts · orders · reviews

Why keep them separate?

Because they have different jobs and different risks. The frontend can be rewritten without touching the data. The backend enforces rules the browser cannot be trusted with — a visitor could edit the page in their browser and set a price to ₹1, but the backend recalculates the real price before saving the order, so it does not matter.

Say this out loud

"The frontend never trusts its own numbers. When you check out, the browser sends only the product IDs and quantities. The backend looks the real prices up in the database and recalculates the total itself. That way the price cannot be tampered with."

A real example: what happens when you click "Add to cart"

  1. You click the green + button on a product card.
  2. The frontend sends POST /api/cart/items with {product_id: 5, quantity: 1}.
  3. The backend checks: does this product exist? is it still in stock? If there are only 3 left and you asked for 4, it refuses and sends back the message "Only 3 left in this batch."
  4. If you are logged in, it finds the cart attached to your account. If not, it uses a random token stored in your browser, so guests get a cart too.
  5. It saves the row, then recalculates the subtotal, the delivery fee (free over ₹799), and the total.
  6. It sends the whole updated cart back as JSON.
  7. The frontend updates the cart badge in the corner, pops the number, and shows a small toast saying "Mango Pickle added".

05

How the database is designed

Nine tables. Every one exists for a reason, and the reasons are the interesting part.

TableHolds
usersName, email, phone, and the hashed password.
addressesSaved delivery addresses. One user can have many.
categoriesThe five shelves — masalas, pickles, fresh batters, snacks, sweets.
productsThe fourteen items: name, price, stock, spice level, description, ingredients, photo.
cartsOne open cart per user — or per guest, keyed by a random browser token.
cart_itemsOne row per product in a cart, with its quantity.
ordersA confirmed purchase: totals, payment status, and the delivery address.
order_itemsWhat was actually in that order.
order_eventsOne row each time the order changes status. This is what the tracking timeline reads.
reviewsStar rating and text. One review per person per product.
contact_messagesMessages sent through the contact form.

Three design decisions worth explaining

Say this out loud

1. Why order_items copies the product name and price

It looks like duplicated data, and it is deliberate. If the price of Mango Pickle changes next month, a customer's old invoice must still show what they actually paid. So the order stores its own copy. The same goes for the delivery address — editing your saved address must not rewrite where a past parcel was sent. This is called snapshotting.

Say this out loud

2. Why there is a separate order_events table

The order could just have a "status" column. But then you would only know where it is now, not when it was packed or when it shipped. A separate table with one row per change gives a full history, which is exactly what the tracking timeline displays.

Say this out loud

3. Why guests get a cart too

Forcing people to sign up before they can add anything to a basket loses sales. So a guest cart is stored against a random token in the browser. When that person later signs in, the backend merges the guest cart into their account cart instead of throwing it away.

Relationships, in one line each

  • A category has many products. A product belongs to one category.
  • A user has many addresses, many orders and many reviews.
  • A cart has many cart_items; each points at one product.
  • An order has many order_items and many order_events.
  • A review joins one user to one product — and the database enforces that a person can only review a product once.

If asked "why does it look like this?", the answer is not "it looks nice". Every choice comes from the subject.

The three signature ideas

Glassmorphism Cards are frosted glass because a pickle jar is glass — you shop by looking through it. Not a trend pick; it comes from the product.
Claymorphism Buttons are soft and puffy with a hard bottom edge that compresses when pressed, so they feel like objects you push.
The masala mesh Five spice-coloured blobs drift slowly behind the whole site. Every frosted surface is showing you that, blurred.
Kolam The rice-flour pattern drawn on a South Indian doorstep every morning. Used as a motif — and because it is a real dot grid, it earns its place.

The typefaces

  • Bricolage Grotesque — all headings. Modern and slightly irregular.
  • Instrument Sans — body text. Quiet and very readable.
  • Baloo Thambi 2 — the "KaiRuchi" wordmark. Chosen because it was designed alongside Tamil script, so the brand name sits in a face built for its own language.

The animation, and its limits

Lenis drives all scrolling. On top of it: a loading screen that draws a kolam, words that rise into place, section reveals as you scroll, magnetic buttons, cards that tilt in 3D with a moving highlight, and letter-by-letter flips on the menu.

Say this out loud

"Every animation respects the operating system's prefers-reduced-motion setting. If a visitor has asked their device to reduce motion — often for motion sickness or vestibular disorders — all of it switches off automatically. Accessibility was built in, not added afterwards."

The photographs

All 21 product and category photographs, and the hero film, were generated with Higgsfield (Nano Banana Pro for stills, Seedance 2.5 for video). They arrived as 4K PNGs totalling about 200 MB, which would make the site unusable, so a script converts them to WebP at the size they are actually displayed — 2.6 MB for the whole set, a 99% reduction.

08

The payment system — read this carefully

Important

No real money moves, and no card details are ever collected.

The checkout opens a payment sheet that is clearly labelled "Demo gateway · no real payment". It has no fields for a card number, UPI ID or bank login — deliberately, so there is nothing to enter and nothing to leak. Choosing a method and pressing pay simply tells our own backend that the order was paid.

Why it is built this way

Taking real payments requires a registered business with a payment provider. This is a college project, so it simulates that step instead. There is also a "Simulate a failed payment" button, so the error path can be demonstrated too — not just the happy path.

But the real integration is written

The code for Razorpay, India's standard payment gateway, is fully written in backend/app/services/payment_service.py: creating a gateway order, and verifying the payment signature using HMAC-SHA256 so a fake confirmation cannot be faked. It stays switched off unless real API keys are configured.

Say this out loud

"Payments run in mock mode by default. The Razorpay integration is implemented, including HMAC signature verification, but it only activates when API keys are supplied. That way the whole checkout flow can be demonstrated end to end without a merchant account, and without ever handling card data."

Cash on delivery

The second payment option is genuine and needs no gateway at all — the order is confirmed immediately and marked to be paid to the courier.

Setting it up on your computer

From nothing to a running website. Do these in order — each step assumes the one before it worked.

Step 0 — install these four things first

InstallGet it fromHow to check it worked
Gitgit-scm.comgit --version
Node.js (v20+)nodejs.orgnode --version
Python 3.12python.orgpython --version
PostgreSQL 16postgresql.orgRemember the password you set during install
Watch out

When installing Python on Windows, tick "Add Python to PATH" on the very first screen. If you miss it, none of the python commands below will work and you will have to reinstall.

Step 1 — get the code

Open a terminal (on Windows: Git Bash or PowerShell) and run:

# Download the project from GitHub
git clone https://github.com/niri2630/kai-ruchi.git
cd kai-ruchi

Step 2 — create the database

# Creates an empty database called kairuchi
psql -U postgres -c "CREATE DATABASE kairuchi;"

It will ask for the PostgreSQL password you chose during installation.

Step 3 — set up the backend

cd backend

# A private Python environment, so this project's packages
# do not clash with anything else on your computer
python -m venv .venv

# Install everything the backend needs
.venv/Scripts/python -m pip install -r requirements.txt

# Copy the settings template
cp .env.example .env

Now open backend/.env in any text editor and make sure the database line matches the password you set:

DATABASE_URL=postgresql+psycopg2://postgres:YOUR_PASSWORD@localhost:5432/kairuchi

Then build the tables and fill in the products:

# Create all the tables (this is Alembic doing the migration)
.venv/Scripts/python -m alembic upgrade head

# Load 14 products, 5 categories, 6 demo users and 16 reviews
.venv/Scripts/python -m app.seed

Step 4 — set up the frontend

cd ../frontend

# Install everything the frontend needs (takes a few minutes)
npm install

# Copy the settings template
cp .env.example .env.local

Step 5 — run it

You need two terminals open at the same time. This is the part people get wrong: the backend and the frontend are two separate programs.

Terminal 1 — the backend 
cd backend
.venv/Scripts/python -m uvicorn app.main:app --reload --port 8000

Leave it running. Check: 127.0.0.1:8000/docs

Terminal 2 — the frontend 
cd frontend
npm run dev

Leave it running. Open: localhost:3000

Demo login

Email meera@example.com, password kairuchi123. All six demo accounts use the same password. The sign-in page also has a "Fill in demo credentials" button, so you do not have to type it during a demo.

When something goes wrong

What you seeWhat it means and how to fix it
"The kitchen isn't answering" on the website The frontend cannot reach the backend. Almost always: the backend terminal is not running. Start Terminal 1 again.
Products are missing but the site loads The tables exist but are empty. Run python -m app.seed again.
python: command not found Python is not on your PATH. Reinstall Python and tick "Add Python to PATH".
password authentication failed The password in backend/.env does not match your PostgreSQL password.
port 3000 is already in use The site is already running in another terminal. Close it, or let Next.js use port 3001.
Login stops working after a restart The SECRET_KEY in .env changed, which invalidates every issued token. Just sign in again.
CORS error in the browser console The backend is refusing the frontend's address. Add that address to CORS_ORIGINS in backend/.env.
The first thing to check, always

Open http://127.0.0.1:8000/health. If it says "database":"connected", the backend and database are both fine and the problem is in the frontend. If it does not load at all, the backend is not running.

Questions your teacher will ask

Answer in your own words — but these are the points that matter.

Why did you split the frontend and backend instead of building one program?
So each can be changed, tested and deployed independently, and so the rules live somewhere the user cannot edit. The same backend could serve a mobile app later without rewriting anything.
How are passwords stored?
They are not. Each password is hashed with bcrypt, which is one-way — you cannot reverse it. When someone logs in we hash what they typed and compare the hashes. bcrypt also adds a random salt, so two people with the same password get different stored values.
How does the site know I am logged in?
On login the backend issues a JWT — a token signed with a secret key. The browser stores it and sends it with every later request. The backend verifies the signature. If anyone edits the token, the signature stops matching and it is rejected.
What is Alembic and why not just create the tables by hand?
Alembic records every schema change as a file. That means the database can be rebuilt identically on any machine with one command, changes can be undone, and the history is in version control alongside the code. Creating tables by hand is not repeatable and cannot be reviewed.
What stops someone changing the price in their browser and paying ₹1?
The browser never sends prices. It sends product IDs and quantities. The backend looks up the real price in the database and recalculates the total itself. It also re-checks stock at that moment, so two people cannot buy the last jar.
Is the payment real?
No, and that is deliberate — a real gateway needs a registered business. The checkout runs a clearly-labelled simulation that collects no card details at all. The Razorpay integration is written, including HMAC signature verification, and activates only if API keys are supplied.
How does order tracking work with no admin panel?
Each status change is saved as a row in order_events, and the timeline reads that history. Because there is no staff to click the buttons, a paid order advances on a timer over about 35 minutes so it can be demonstrated live.
How do you know a review is genuine?
When a review is submitted, the backend checks whether that user has an order containing that product. If so it is flagged verified purchase. A database constraint also allows only one review per person per product.
Is it responsive?
Yes, and it was tested by measuring the real page at 375 pixels, not by eye. Two real bugs were found and fixed: form fields under 16px caused iOS Safari to zoom the whole page on focus, and the quantity buttons were below the 44-pixel touch target.
What was the hardest part?
A good honest answer: making the cart work for both guests and logged-in users, and merging one into the other at sign-in without losing or duplicating items.
What would you add next?
An admin dashboard so orders and stock can be managed properly, real payments, email notifications, and automated tests.
